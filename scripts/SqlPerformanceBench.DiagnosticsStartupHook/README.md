# Fixture runtime diagnostics startup hook

Build with `dotnet build scripts/SqlPerformanceBench.DiagnosticsStartupHook/SqlPerformanceBench.DiagnosticsStartupHook.csproj`. This standalone net10.0 library uses the ASP.NET shared framework and adds no packages or application project references.

Use only on an isolated owned benchmark API fixture. Set `DOTNET_STARTUP_HOOKS` to the absolute DLL path, `PERFBENCH_RUN_ID` to the fixture GUID in N format and `PERFBENCH_DIAGNOSTICS_OUTPUT` to an absolute directory outside all Git checkouts. Missing or invalid opt-in settings make initialization a no-op. Startup hook environment variables must be scoped to that child process. The fixture runner remains responsible for validating database ownership.

Load requests must send `X-PerfBench-Request-Id: perf-load-<client>-<step>` (ASCII alphanumerics and hyphens, maximum 96 characters). The hook correlates ASP.NET start/stop and EF events using `Activity.Current.TraceId`. Only requests with that prefix produce request/command/connection records. Counters represent the complete fixture process, including other fixture traffic.

The JSON file `runtime-<runId>-<processId>.json` is atomically replaced every five seconds and flushed on normal process exit. Existing evidence is never overwritten at startup. At most 100,000 records are retained; dropped record counts, unmatched operations, active requests and observed event counts make truncation or missing instrumentation visible. No SQL text, parameters, connection strings, profile values, URLs, query strings, bodies, headers or tokens are persisted. Request identifiers are strictly limited to synthetic load correlation identifiers. Instrumentation exceptions are isolated from application execution.

For multiple load stages in one fixture process, the runner can atomically write `<output>/window.json` containing `{"runId":"<fixture GUID N>","window":"mixed-25-pass1"}` before each stage. The hook polls this control every second. It accepts only matching run ownership, files up to 4096 bytes and labels of 1–64 ASCII alphanumeric/hyphen characters. A changed label flushes the old window, resets its bounded records and switches to `runtime-<runId>-<processId>-<window>.json`; existing destinations are refused. Each repeated stage requires a fresh label. Five-second snapshot cadence continues within the new window. Metadata records the window start; observed event counts remain explicitly process-cumulative. Pending requests/operations survive rotation, so drain the previous workload and allow a warmup interval after control publication before sampling the new workload.

## Events and payloads

`DiagnosticListener.AllListeners` replays existing listeners and subscribes to newly created listeners. Listener names are `Microsoft.AspNetCore` and `Microsoft.EntityFrameworkCore`.

- `Microsoft.AspNetCore.Hosting.HttpRequestIn.Start` / `.Stop`: payload `HttpContext`, current activity trace ID, response status. Stopwatch elapsed measures the hosting pipeline interval.
- `Microsoft.EntityFrameworkCore.Database.Connection.ConnectionOpening` / `ConnectionOpened` / `ConnectionError`: payload `ConnectionId`, completion `Duration`. Opening-to-opened duration measures acquisition through EF/SqlClient Open; failures are retained.
- `Microsoft.EntityFrameworkCore.Database.Command.CommandExecuting` / `CommandExecuted` / `CommandError`: payload `CommandId`, `Command` used only for coarse classification in memory, completion `Duration`. Stored labels are count/page/summary/write/unknown and contacts/leads/tasks/other/unknown. Classification is heuristic, especially for composite SQL.
- `Microsoft.EntityFrameworkCore.Database.Command.DataReaderDisposing`: payload `CommandId` and numeric `ReadCount`, correlated to a `CommandExecuted` payload whose `Result` is a data reader. A separate stopwatch measures executed-to-disposing elapsed time as `reader-consumption`; the event's `Duration` is deliberately not added to command duration. This span includes row reading, EF materialization and scheduling between those events; it does not isolate mapping CPU. `ReadCount` counts read operations and is not guaranteed to equal returned rows. Unfinished readers are reported separately as `pendingReaders`.
- EventSource `System.Runtime` and `Microsoft.Data.SqlClient.EventSource`, `EventCounters`: dictionary payload `Name`, `Mean` or `Increment`, `IntervalSec`. A one-second counter interval captures available GC, allocation, heap, thread-pool, CPU and SqlClient pool counters without assuming every runtime/provider emits every counter. Actual observed counter names appear in the JSON.

EF payload shapes were checked against locally installed EF Core relational XML documentation. The project build verifies framework compatibility; the fixture runner must verify actual emitted event names and coverage before interpreting a load run.

## Interpretation limits

Connection acquisition duration can include pool contention, physical connection creation, authentication and network work. It is not an isolated pool-wait measurement. Command execution duration for a reader can exclude subsequent row materialization and reader consumption. HTTP start/stop does not establish time spent queuing before the ASP.NET pipeline. Thread-pool queue length is evidence of queued work, not proof of starvation; confirm with throughput, CPU and timing. Counters are sampled process-wide and have different units and mean/increment semantics; preserve provider definitions when aggregating.

Stopping a process forcibly can lose the last five seconds. JSON snapshots and serialization add observer overhead, particularly near the record cap, and may perturb latency. Run matched instrumented comparisons, use dedicated evidence directories, and report these limits. This helper changes no production logging configuration or business behavior and must never be injected into an existing business API process.
