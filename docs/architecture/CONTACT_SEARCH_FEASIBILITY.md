# Contact search feasibility

This investigation keeps the current production baseline. Its two independent experiments live only in `scripts/SqlPerformanceBench`; neither is registered in application DI, selected by search length, or represented by a production migration. Evidence belongs in a fresh external directory. Actual measurements and cleanup state are recorded by the run, rather than inferred from a successful build.

## Query-only candidate selection

`--search-feasibility` compares the canonical query with two explicit page shapes. Both retain the original workspace, record scope, readable search fields, filters, Tasks predicates, cursor boundary, TOP limit and ordering inside candidate selection. The outer query joins the candidate Workspace/Contact keys to the full Contact row. Count and status summary SQL remain unchanged. One shape leaves index selection to SQL Server; the other forces the existing Contact primary key only within candidate selection. Neither adds a table, projection, trigger, token index or global row-goal hint.

A derived table does not guarantee materialization. Inspect the saved actual plans for qualifying Contact lookup executions and the outer fetch, rather than assuming fewer lookups from the SQL text. A clustered scan can reduce sparse-result reads while adding work for common searches. Unchanged count extraction also limits the combined persistence benefit. Paired samples, reverse-order repeats and per-command replay distinguish those costs from shared-host variance.

The 2026-10-09 fixture measured 10K common p95 at 18.17/18.57/40.46 ms for baseline/unhinted/clustered, with reverse-order repeat 18.87/18.24/40.64 ms. At 100K, common was 37.23/36.87/114.23 ms, rare 1,979.39/1,968.99/1,041.46 ms and no-match 4,046.05/3,883.89/949.84 ms. These are combined persistence-call samples on a shared host, not endpoint latency. Sparse-search gains for the clustered variant are real measured benefits, accompanied by common-search regression; no workload weighting or acceptance envelope admits that tradeoff.

In the 100K rare page plan, baseline and unhinted selection both perform 20,252 qualifying Contact lookups; the unhinted shape adds 26 full-row seeks. The clustered variant replaces qualification lookups with a scan and retains 26 full-row seeks. Page logical reads are 62,785/62,872/11,005, while count remains 10,549 reads. This explains why the SQL-only unhinted shape does not achieve its intended lookup reduction. Per-operator scan counters can include parallel execution; they are not distinct Contact counts.

Differential checks cover SQL JSON/Unicode behavior, readable fields, Workspace/OWN scope, exact count, status summaries, Tasks authority, three sorts and continuation. Sequential committed insert/delete/update checks exercise live pages. These controlled fixture inputs do not establish public HTTP authorization or every concurrent interleaving.

In particular, the fixture uses locking READ COMMITTED, with RCSI disabled and snapshot isolation off. Qualification followed by a second Contact read in one command does not establish a frozen row view. Qualification-to-materialization parity during an interleaved owner/profile/order change remains **NOT_ESTABLISHED**. The baseline already has separate live count/page commands; no snapshot guarantee is introduced. This admission gap and the measured workload tradeoffs prevent production promotion.

## EF and trigger compatibility

`--ef-trigger-feasibility` runs the independent write experiment at 10K. It first captures canonical SQL without a trigger, then captures the same canonical model with a synthetic-workspace projection trigger, and finally uses a separate benchmark DbContext model with `UseSqlOutputClause(false)` on Contacts. The compatible context copies canonical mappings and changes only this provider setting. It does not change the sealed application context, application DI, persistence adapter, or migration ownership.

The enabled trigger conflicts with SQL Server's bare UPDATE OUTPUT path: canonical update and archive reproduce SQL error 334. The experiment verifies unchanged rows/version after those rejected writes. Disabling OUTPUT in the isolated model allows provider row-count handling; capture the actual SQL to verify this rather than attributing the failure to JSON extraction or business validation. Canonical create is checked independently because its generated command can differ from update.

Lifecycle checks include create, name/profile/email/phone changes and clearing, owner changes, relationship version mutation, archive, invalid domain input, competing EF contexts with a stale version, and explicit rollback. Reload comparisons cover exact canonical values, normalized email identities, timestamps and version. Projection checks cover SQL scalar values, SourceVersion and delete cascade. Scope remains isolated EF persistence, not public command integration.

The writer inventory includes CreateContact, UpdateContact, ArchiveContact, relationship commands and the NEW-contact path in qualification resolution. Public writers also own authorization, audit, outbox, idempotency and transactional behavior. A direct compatible DbContext does not prove those paths can adopt a changed canonical model. Existing-contact/replayed qualification does not itself mutate a Contact. Public writer compatibility therefore remains PARTIAL until the real persistence adapter and admitted command suite run against the proposed model.

Write measurements compare canonical EF and raw SQL without a trigger, raw SQL and compatible EF with replacement maintenance, and compatible EF with conditional maintenance. Raw values include normalized-email maintenance. The conditional trigger still evaluates SQL scalars to determine whether search data changed; it preserves SourceVersion even on owner/status/version-only changes. It reduces replacement work, not all extraction CPU. Each operation has one warmup and twenty measured transactions. Timing includes begin/commit and a log diagnostic query; sampled pre-commit log bytes are not the complete durable log cost. Status changes use fixture-only SQL/EF writes because no corresponding domain mutator is admitted by this experiment.

Archive tails must be evaluated across baseline/raw/EF modes and sample distributions. A previous archive outlier alone does not establish trigger causality. These measurements are synthetic SQL/EF transaction costs, not HTTP command latency or an accepted write SLO.

The final-source run used SQL Server EF provider 10.0.11 and passed all isolated lifecycle checks for canonical-without-trigger, compatible-with-trigger and compatible-with-conditional-trigger modes. Canonical-with-trigger create passed; update and archive independently reproduced 334 and retained unchanged values/version. Captured commands show canonical `OUTPUT 1` versus compatible `SELECT @@ROWCOUNT`; timestamps and projection deletion were checked explicitly. Both owned databases were cleaned after marker, file and session revalidation. Backend and harness builds passed with zero warnings/errors; six harness timing/concurrency checks passed.

Archive p95 in the final run was 2.03 ms canonical EF baseline, 2.32 ms raw baseline, 3.23 ms raw replacement trigger, 3.04 ms compatible EF replacement and 5.35 ms compatible EF conditional. The first run's corresponding values were 2.86/2.28/1.31/2.95/3.05 ms. The older projection fixture had p95 33.91 ms and p99 61.98 ms, with different normalized-email maintenance scope. That outlier did not recur, but these varying samples do not prove the conditional strategy always improves latency or establish the old outlier's cause. Retain both runs rather than pooling their samples.

## Admission decision

Retain **CURRENT_BASELINE** with **PRODUCTION_PROMOTION: NOT_ADMITTED**. Query-only production admission requires a stable material benefit and controlled concurrent qualification/materialization evidence. Projection admission additionally requires a canonical provider/model decision, complete public writer and policy validation, safe migration/backfill/rollback evidence, and accepted common-search, write and storage tradeoffs. Isolated EF compatibility removes one technical blocker; it does not satisfy those gates.

Resource guards apply during seeding and each measured case. A guarded 100K stop is NOT_ESTABLISHED, even when 10K succeeds. API saturation and 10K concurrent-client capacity are outside this investigation. Ownership markers, managed SQL DATA manifests and session checks govern cleanup; no user database, SQL setting, application configuration or shared cache is changed.

This fixture completed all 63 measurement cases at each of 10K and 100K, including reverse-order common/rare/no-match repeats, matching Unicode and three deep-page sorts. Each candidate passed 98 differential cases and three sequential live-page scenarios at each tier. Thus 100K persistence performance was measured; concurrent API capacity and production admission remain unestablished.

Reproduce with the benchmark README and retain `manifest.json`, seed/resource progress, SQL, parameters, actual plans, IO/TIME, sample distributions, parity/lifecycle results, generated write SQL and teardown evidence together.
