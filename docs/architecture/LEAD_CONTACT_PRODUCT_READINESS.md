## Four confirmed root causes

**Contact detail authority-cache confidentiality, P1, selected.** Detail and relationship-summary resources were keyed by Contact ID or Workspace without the full current principal, membership and access revision. An authority change within the same Workspace could retain a READY response and an old interaction snapshot. Some projection/completion paths also published before validating cancellation and the captured authority. The backend still authorizes fresh reads; the defect is stale frontend data, draft and portal exposure after authority changes.

The selected repair must bind detail/summary resources to full authority scope, reject old reads and mutation projections, quarantine stale mounted forms and portals, and prevent stale global Save or completion proof. It must retain dirty or ambiguous pending intent safely rather than silently discard it. Source boundaries are the frontend `contactAuthoritativeQueries.ts`, `useContactDetailPageController.ts`, `ContactDetailResourceView.tsx` and `useContactRelationshipForm.tsx`. C05, C09 and C10 are manifestations of this single root cause, not three unrelated backend defects. The bounded cache reproduction does not establish a full browser disclosure journey. Executed evidence now covers same-workspace revision/principal changes, dirty/global Save refusal, first-mount projection provenance, delayed old reads/mutations, retired-resource transport refusal, clean/pending recovery preflight, unrelated-draft preservation and explicit standalone form recovery. Chromium verifies nested overlay inert state and absence of suspended input values in the document. Draft ownership remains mounted; these fixture proofs do not substitute for live public backend acceptance.

**Lead connected page-local filter/sort, P1, backlog.** [LeadListPage](../../../frontend/unicorecrm-web/src/modules/leads/presentation/pages/LeadListPage.tsx) composes only search, work state, owner and assignment into its server query. It then runs [useLeadFilters](../../../frontend/unicorecrm-web/src/modules/leads/presentation/hooks/useLeadFilters.ts) on the currently fetched page. Source, campaign, follow-up, outcome, duplicate and team views therefore select from at most the current 50 rows while totals/ranges describe the broader backend result. Sorting name/score/follow-up/created time changes only that page. The default frontend created-time label also differs from fixed backend UpdatedAt/LeadId ordering. Matching later rows may be omitted and cross-page order is not established. No Workspace bypass or write corruption is demonstrated by this finding.

**Lead connected search post-filter, P1, backlog.** The canonical [Lead aggregate](../../src/UnicoreCRM.Crm/Leads/Domain/Lead.cs) projects search text from Lead ID/display name and a separate primary-phone projection that includes normalized digits. The frontend repeats a different search predicate over name/company/email/raw phone. A valid backend ID match, or a digits-only match against a formatted phone, can be removed from the table even while the backend reports a nonzero exact count. Rendering the authoritative backend result removes this false-negative predicate without broadening server search or weakening phone FLS.

**Lead tag removal async proof, P2, backlog.** The remove-tag button in [LeadDetailModals](../../../frontend/unicorecrm-web/src/modules/leads/presentation/components/LeadDetailModals.tsx) invokes Promise-returning `leadActions.update` without awaiting or catching it, then immediately displays success. A delayed or rejected command can therefore appear committed. Global add-tag Save already awaits returned record/tag proof; its sibling remove path needs the same opening-target, pending and typed-error discipline.
